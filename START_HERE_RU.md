# Первая задача разработки: изолированный локальный AI-контроль

Дата: 05.10.2026. Основное ТЗ: `AI_IMPLEMENTATION_SPEC_FINAL_RU_v2.md`. Этот документ определяет первую итерацию и порядок передачи работы разработчику/Cursor. Hermes исключён из проекта.

## 1. С чего начинаем

Создать отдельный локальный сервис, который принимает тестовую переписку, анализирует её и показывает результат с доказательствами. Начать с текста, затем добавить готовые транскрипты и только после этого аудиозаписи и ASR. Так можно проверить предметную логику и устойчивость без тяжёлой модели распознавания на первом шаге.

Первый проверяемый результат: загрузили тестовую переписку → получили краткое содержание, обещания, следующие действия и вероятные процессные проблемы → каждый вывод связан с конкретным сообщением → остановили AI → основная CRM продолжает работать.

Первоначальное извлечение обещаний не доказывает просрочку. Без времени, подтверждения и событий выполнения результат имеет статус proposed/needs_data. Контроль выполнения появится при импорте тестовой временной линии задач и звонков.

## 2. Обязательные границы

- Не менять текущую бизнес-логику, права, стадии, распределение, скорозвон и отправку сообщений.
- Не изменять существующие файлы backend/frontend, основные compose-файлы и зависимости приложения в первой итерации.
- Не подключаться к рабочей БД, Redis, MinIO, телефонии и аккаунтам сообщений.
- Не запускать production миграции, импортёр, polling и реальные webhooks.
- Не совершать внешние звонки, отправки и действия над кандидатами.
- Не использовать Hermes и универсальный агент с произвольными инструментами.
- Не отправлять реальные данные внешним AI-провайдерам без отдельного решения заказчика.

## 3. Размещение и стек

Новая папка `ai-control/` в корне репозитория. Вся реализация первой итерации находится внутри неё. Разрешены дополнения в `docs/ai/`; изменение остальных файлов требует отдельной предметной задачи.

Go API и worker с отдельным go.mod. Для этой малой итерации API и один worker могут быть в одном отдельном AI-процессе: важна изоляция от CRM, а не обязательное дробление AI на микросервисы. Запрос только ставит job; модель вызывается worker, не обработчиком HTTP.

Отдельный PostgreSQL контейнер с отдельным volume и пользователем; отдельный Compose project `crm-ai-local`. Сеть не общая с основной CRM. Не публиковать PostgreSQL port. API публикуется только на `127.0.0.1`, свободный порт выбирается после проверки. Пример стартового порта - 8091; занятый порт не освобождать остановкой другого приложения.

Минимальная HTML-страница, которую отдаёт AI API: загрузка JSON, список заданий, результат и ошибки. Отдельный React/Vite проект и новый раздел основной CRM пока не нужны.

ModelAdapter с двумя режимами:

1. `mock` по умолчанию: воспроизводимые фиксированные результаты для синтетических fixtures; явно помечены как тестовые, не выдаются за настоящий AI.
2. `local`: один явным образом настроенный локальный HTTP endpoint модели, без автоматической установки/скачивания весов. При отсутствии настроенной модели показывать unavailable; не переключаться в облако.

Модель/ASR - отдельный последующий выбор после измерения ресурсов. Нельзя менять конфигурацию работающего AI/CRM сервиса для запуска теста. Local endpoint проверяется allowlist; произвольный URL из пользовательского файла не допускается.

## 4. Входные данные

JSON conversation: source_id, source_version, lead_ref как тестовый идентификатор, timezone, messages[].

Каждое сообщение содержит message_id, author_role (`manager`, `candidate`, `unknown`), occurred_at RFC3339, text. Идентификаторы должны быть уникальны в conversation. Не передавать токены, реальные номера и паспортные значения. По умолчанию загружаются только синтетические примеры.

В первой итерации: максимум 1 MiB JSON, до 200 сообщений, до 8 000 символов в сообщении и до 100 000 символов суммарно. Это стартовые ограничения тестового сервиса, не ограничения CRM. Файл сверх лимита отвергается до постановки в очередь. Проверять допустимые роли, timestamps, timezone и source_version.

Проверка безопасности текста выполняется до model adapter. Результат mock/local проходит одинаковую строгую валидацию и проверку ссылок на существующие сообщения. Отсутствующий источник не подменять выдуманным доказательством.

## 5. Выходные данные

- analysis_id, job_id, source_id/version, mode, pipeline/model/prompt/schema versions;
- status: completed, partial, failed, needs_data;
- safe_summary;
- proposed_promises: тип, автор, time_expression, условие, evidence_message_ids;
- suggested_next_actions: рекомендация и источник, без выполнения;
- signals: категория, правило, safe explanation, evidence_message_ids, uncertainty;
- coverage, created_at, latency и safe error code.

Автор неизвестен → персональная ответственность неизвестна. «Не отправляйте паспорт в чат» → предупреждение, а не запрещённый запрос. Слова кандидата не считаются обещанием/нарушением менеджера. Не выводить балл сотрудника или прогноз пригодности кандидата.

Начальные `contracts.schema.json` служат каталогом целевых контрактов. Для малого входа conversation разработчик добавляет отдельную версионированную JSON Schema внутри ai-control, не изменяя смысл существующих контрактов. Envelope IDs/versions устанавливает сервер; ответы модели не считаются доверенными серверными метаданными.

## 6. API и jobs

| Endpoint | Назначение |
|---|---|
| GET /healthz | процесс жив |
| GET /readyz | БД доступна, worker готов; model status указан отдельно |
| POST /v1/conversations | validate + сохранить source + создать job в одной транзакции, ответ 202 |
| GET /v1/jobs/{id} | state/progress/safe error |
| GET /v1/jobs | ограниченный список тестовых jobs |
| GET /v1/analyses/{id} | валидированный результат |
| POST /v1/jobs/{id}/retry | повтор failed job с ограничением попыток |

API требует отдельный локальный токен из env/config; HTML использует его в памяти без URL/query string. Не брать JWT основной CRM. В state-changing browser requests проверять Origin; CORS не открывать произвольным сайтам. Логи не содержат token/raw text/model prompt. Это базовая защита локального стенда, не полноценная production-auth CRM.

Job states: queued → running → completed / failed / cancelled. Lease/heartbeat, idempotent key source_id + source_version + pipeline_version + mode. Повторный запрос с тем же key и другими данными → conflict. Сохранённый результат не дублируется после рестарта.

Timeout одной попытки: 60 секунд как тестовый default, max 2 автоматических retry с backoff. До 100 незавершённых jobs; при заполнении 429/queue_full без потери уже принятых заданий. Уточнить значения после ресурсного прогона; конечные лимиты обязательны.

## 7. Ресурсы и остановка

Concurrency = 1. Для mock: стартовый предел AI API/worker 1 CPU / 512 MiB RAM; тестовый PostgreSQL 0.5 CPU / 512 MiB RAM, connection pool максимум 3. Эти лимиты не включают модель и не являются гарантией достаточности конкретного компьютера. До запуска убедиться в наличии резерва CRM/ОС.

Local модель запускается только после отдельной оценки памяти; её ресурсный бюджет ограничивается отдельно. Не запускать тяжёлую модель просто потому, что API успешно работает. GPU/unified memory на Mac также учитывается в общем бюджете.

Ограничить request sizes, response sizes, DB pool, job count, temp files и rotation логов. Data directory имеет настраиваемый конечный бюджет, для mock начать с 256 MiB; перед каждым сохранением проверить свободное место/бюджет, при превышении отказать новым заданиям. Не полагаться на volume как автоматическую disk quota.

AI выключен по умолчанию; никакого запуска вместе с основной CRM. Для первого стенда restart policy выключена. Graceful stop завершает/возвращает job согласно lease, не останавливает другой Compose project. Команда остановки нацелена только на crm-ai-local; не применять общий docker stop/prune.

## 8. Порядок работ

| Шаг | Работа | Что сдаёт разработчик |
|---|---|---|
| 0 | Read-only baseline: структура, существующие проверки, занятые порты, CPU/RAM/disk | короткий baseline report; никаких секретов |
| 1 | ai-control skeleton, отдельные DB/Compose/config, health endpoints | запускается вручную в mock, основная CRM не изменена |
| 2 | schemas, sources/jobs/result storage, worker lease/idempotency | API и восстановление очереди |
| 3 | mock corpus и UI | полный загрузка → job → evidence result |
| 4 | local ModelAdapter и строгая валидация, без запуска тяжёлой модели | подключается к явно настроенному endpoint, timeout/errors видны |
| 5 | fault/resource tests, README и итог изменений | протокол проверки и команды запуска/остановки |

После приёмки: настроить локальную модель → проверить смысловой анализ → импорт готовых транскриптов → ASR для сохранённых тестовых аудио → тестовые события задач/лидов → процессные таймеры → подключение к локальной копии CRM. Рабочую CRM подключать только отдельной задачей.

## 9. Синтетический корпус

Минимум 12 fixtures: обычный разговор; явное обещание перезвонить; условное обещание; относительная дата; неизвестная зона; слова кандидата; безопасное предупреждение про паспорт; запрещённый запрос менеджера без реальных реквизитов; unknown author; prompt injection; отсутствие evidence; повторный импорт.

Fixtures имеют ожидаемые классы и references. Mock проверяет pipeline и интерфейс, не качество настоящего LLM. Семантическая точность оценивается отдельно в local mode на независимом корпусе.

## 10. Критерии приёмки первой итерации

1. Изменения только в ai-control/ и docs/ai/; runtime основной CRM не меняется.
2. БД, volumes, credentials, ports и network отделены от CRM.
3. Корпус загружается, анализ ставится в очередь и результат имеет корректные references.
4. Mock помечен явно; local mode без endpoint не изображает успешный анализ.
5. Невалидные схемы/роли/слишком большой вход отвергаются.
6. Повторный импорт/рестарт не создают дубли.
7. Timeout/invalid JSON/отказ модели показаны, worker не зависает бесконечно.
8. Concurrency/resource/queue/disk limits проверены; нет неконтролируемых retry.
9. Падение/остановка AI не меняет CRM и не останавливает её процессы.
10. Нет реальных звонков/сообщений, production connections и передачи реальных данных.
11. До/во время/после анализа проверены одинаковые операции локальной CRM; latency/errors и ресурсы записаны. При отсутствии запущенной локальной CRM этот пункт обозначается непроверенным, а не пройденным.
12. Есть README с точными командами, config example без секретов, test report, dependency список и инструкция восстановления jobs.

Тесты должны проверять идемпотентность, lease recovery, limits, errors и evidence validation. Не заменять их демонстрацией mock happy path. Полный основной набор проверок CRM не выполнять без необходимости; определить релевантный baseline и убедиться, что существующие файлы не изменены.
